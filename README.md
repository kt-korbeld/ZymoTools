## Overview
A suite of tools for generating de novo zymogen or prozyme designs using BindCraft, BoltzGen or
RFdiffusion3. It takes a target structure, proposes hotspot patches for binder
design to cover an active site, lets you curate them, runs a self-managing hotspot screen on SLURM, and
sizes a fusion linker for the designs you keep, and finally fuses the designs with a linker to create the final artificial zymogens.

```
structure ─► hotspots  ─►  screen  ─► linker ─► fuse
                 │                      │
           view-hotspots           view-linker
```
These steps are integrated in the following command-line tools:

```
hotspots           Find patches, write `patch_summaries.csv`, and generate input files for the selected backend.
rfd3-job           One integrated RFdiffusion3 design round. Called by screen rfd3.
screen bindcraft   Run/continue the self-resubmitting SLURM screen for BindCraft.
screen boltzgen    Run/continue the self-resubmitting SLURM screen for BoltzGen.
screen rfd3        Run/continue the self-resubmitting SLURM screen for RFdiffusion3.
status             Report progress per input for any of the three backends.
linker             Shortest-solvent-path fusion-linker length between two residues.
fuse               Fuse directory of binder-target structures into one chain and construct linker
view-hotspots      Run local Shiny app to inspect patches and export a curated CSV.
view-linker        Run local Shiny app for interactively visualizing the shortest linker length.
patch-bindcraft    Implement a patch to BindCraft to add new termini loss
run                Run the whole pipeline: hotspots, pause for curation (default) or `--auto` continue into screen.
```

Add `-h` to any command for its full options.

## Installation
The suite can be installed using pip:
```bash
pip install zymotools[all]
```
Or can be run without proper installation run using: 
```bash
python run_zymotools.py <command> [options]
```
The latter option allows for a more modular deployment, as not all commands require the same dependencies.
especially the `rfd3-job` and `screen` commands can often be run without requiring a separate environment:

```
hotspots      numpy, pandas, pyyaml, Biopython, MDAnalysis
rfd3-job      numpy, pyyaml
screen        numpy, pyyaml
linker        numpy, scipy, MDAnalysis
fuse          numpy, scipy, MDanalysis, pyDisgro
view-hotspots numpy, MDAnalysis, Shiny
view-linker   numpy, scipy, MDAnalysis, Shiny
run           numpy, pandas, scipy, pyyaml, Biopython, MDAnalysis, pyDisgro, Shiny
```

The suite assumes the BindCraft/BoltzGen/RFdiffusion3 backends are installed separately in an appropriate environment.
For RFdiffusion, the suite assumes the use of [foundry](https://github.com/RosettaCommons/foundry) 
to install the RFD3/MPNN/RF3 models. For [BindCraft](github.com/martinpacesa/BindCraft), and 
[BoltzGen](https://github.com/HannesStark/boltzgen), the installation instructions on their 
respective github pages should be followed. Running the `patch-bindcraft` command implements a 
patch that adds a loss function to BindCraft to force the target-binder termini closer.
This command assumes access to the UNIX `patch` command. 

The SLURM screening phase can run for days, so the `screen` command resubmits itself. For this,
it needs access to the correct installation enviroment during resubmission. This is handled 
by the script, so the  code can safely be installed in its on virtual environment. 
Some additional parameters might need to be specified for particular backends. 
These are listed under `-h` for each of the respective pipelines. 


## Typical run

**1. Generate hotspots**

a typical command to generate hotspots and their corresponding input files looks like:
```bash
zymotools hotspots --struc struc_1.pdb --pipeline bindcraft --chain A --outdir runs/hotspots
```
`--pipeline` picks which backend the per-patch settings files are written for
(`bindcraft`, `boltzgen` or `rfd3`). It also sets a default patch size: BindCraft prefers
larger patches, while BoltzGen and RFdiffusion3 conventionally take a handful of hotspot residues.
The `--depth` and `--minsize` parameters can be increased to create larger patches.
the defaults are (`--depth 3 --minsize 6`) for BindCraft, and (`--depth 1 --minsize 2`) for BoltzGen/RFD3.

The tool writes a summary of each of the patches in `patch_summaries.csv`, 
one input file for the next step as `*-patch-N.json` (BindCraft) or `*-patch-N.yaml`
(BoltzGen, RFdiffusion3) per patch in score order, and an `inputs-out.txt` file listing 
each input file ranked in order of most favorable patch, and a `pipeline.json` recording the run.
Backend-specific templates to base the input files on are generated by default, but can also be provided. 
To make sure the patches cover specific residues, the flag `--target 156 157 158 …` can be specified.

**2. Inspect hotspots (optional)**

The generated hotspots are ranked from best to worst. As a result, similar hotspots are frequently ranked 
close together. This might be desirable, but to increase a diversity in sampling, a few diverse hotspots can be
manually curated. To inspect the hotspots and select a desirable set, use:
```bash
zymotools view-hotspots
```
This will open an interactive hotspot viewer in your local browser. This therefore should not be run on an 
HPC cluster without access to a browser. Select the patch rows you want and "Download selected rows as CSV". 
You can trim `jsons-out.txt` to just the patches you intend to run.

**3. Screen hotspots**

A typical command to screen the hotspots will vary between backends. For BindCraft, this will look like:
```bash
zymotools screen bindcraft --inputs runs/struc_1/inputs-out.txt --bindcraft /scratch/user/bindcraft
```
When using the `bindcraft` pipeline, the `--bindcraft` flag specifies the folder where bindcraft is installed. 
options for most input files, such as `--slurm-bc`, `--filters` and `--advanced` default to standard locations 
within the bindcraft folder. The default bindcraft slurm already handles environment activation. The screen submits 
jobs for the hotspots in the order specified in the `--inputs` text file and reschedules itself. The script goes 
down the list until sufficient designs are generated. An input is considered finished when enough final designs exist 
(`number_of_final_designs`), or enough trajectories have run (`--min-traj`, default 300) 
with too low a success rate (`--min-ratio`, default 0.01).

When using running the `boltzgen` pipeline, the `--boltzgen` flag should instead specify the activation command 
for the boltzgen environment. When using the `rfd3` pipeline, this activation command should be passed to `--foundry`,
and `--checkpoints` should specify the folder with the model checkpoints. Since no default binder pipeline is available
for RFdiffusion3, an in-house pipline is used which is implemented under the `rfd3-job` command. It and the `screen` 
command have the following flags for binder design cutoffs during refolding:
```
--min-iptm    (0.8) the minimum ipTM between target-binder
--min-plddt   (80)  the minimum pLDDT of the binder
--max-ipae    (10A) the maximum of the min PAE between target-binder
--max-rmsd    (2A)  the maximum RMSD between the RFD3 model of the binder and the RF3 refold
```

To check the progress of the current screen, run:
```bash
zymotools status --outdir runs/struc_1
```
Any parameter can be named explicitly instead:
```bash
zymotools status --inputs inputs-out.txt --pipeline boltzgen --screen-outdir runs/9I8E/boltzgen-screen --budget 300
```

**4. Estimate linker size (optional)**

The required linker length can be estimated by calculating the shortest path around the protein. 
This is done by creating a solvent grid around the protein and finding the shortest path using a Dijkstra search.
A typical command to estimate the linker length is:
```bash
zymotools linker --struc design.pdb --chain-start A --start 108 --chain-end   B --end   1
```
Reports the shortest path around the protein and the minimum linker length in residues.

**5. Fuse designs into the final constructs**

This final step filters the output structures for those where the separate binder and target chains 
can be combined into a single-chain construct with a flexible linker: the C-terminus of one segment, 
a flexible linker, then the N-terminus of the other. It does this by first filtering using the linker 
length estimation implemented in `linker` and then constructing the linker using 
[pyDisgro](https://github.com/kt-korbeld/pyDisgro), our python port of 
[Disgro](https://github.com/aa14k/Disgro). A typical command to fuse the binder looks like:

```bash
python pipeline.py fuse --struc runs/struc_1/accepted/ --outdir runs/struc_1/fused
```
Where `--struc` specifies either an input structure or directory with input structures.
The linker defaults to `GGGSGGGSENLYFQS`: flexible GS spacer plus a TEV site, 
so the halves can be separated again after expression, resulting in a a 15-residue linker.
Other linkers can be set using `--linker` and are limited to a maximum length of 18-residues.
If the target or binders have flexible N- or C- termini that should be optimized alongside 
the linker, the `--optimize-term` flag can be added. If these flexible termini should be 
overwritten by the linker, use `--replace-term` instead. `--check-only` does the linker length calculation only. 
The output are s one construct per design plus a `fusion_report.csv` reporting every design including the rejects.

## Notes and caveats
- the input structure should be well-prepared. if a crystal structure is used, co-solvents should be removed,
  and missing residues added. The structure should match whatever will be expressed experimentally:
  if terminal residues are left out there, they should be left out during the design process.
- The current pipeline has only been verified and tested experimentally for BindCraft. 
  BoltzGen and RFD3 pipelines have not been extensively run or experimentally tested so particular
  cutoffs and settings might not be well optimized. Especially for RFD3, the used cutoffs are
  tentative, and might need to be changed or adjusted accordingy.
- The foundry API for MPNN and RF3 are unstable, and its RF3 CLI is undocumented.
  Some of the default scripts in rfd3_io might need to be changed if this API is updated.
- Running the foundry models for RFD3 by default uses a shim for running on the HPC cluster.
  This is to prevent an error which occurs when the some of the checkpoints try to call a nonexistent cache.
  This should normally just produce a warning, but can sometimes result in an error.
  Point `FOUNDRY_RESIDUE_CACHE_DIR` at a real cache to use one.
- The shim is optional. Both the error and shim are specific to the machine and foundry
  version used, so `rfd3-job --foundry-shim off` (or `BINDER_PIPELINE_FOUNDRY_SHIM=off`)
  calls `rfd3`/`mpnn`/`rf3` directly instead.
- Code for the different commands in the suite was written and tested manually, and further
  tested and refactored into one package using claude. The shim and bindcraft_patch were written using claude.
